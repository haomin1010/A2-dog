# 风险登记

> 记录已识别、尚未处理的风险。推进到相关阶段时先评估这里，再决定方案。

## R1 ⚠ 本地算力不足（阶段 2/3 视觉）— 待评估

**状态**：已识别，未处理。**进入阶段 2 前必须评估。**
**记录日期**：2026-11-20

### 事实
- PC2：i7-1355U（2 性能核 + 8 能效核，12 线程），只有核显 Iris Xe，**没有任何 AI 加速卡 / 独显 / NPU**（已核对全部 PCIe/USB 设备）。
- 服务器：同样**没有 GPU**。整个系统唯一的"大算力"是云端（通义）。
- PC2 上已常驻：自带 SLAM 三个进程（约 0.5 核）、实时内核（上下文切换约 10 万次/秒）。
- 软件：onnxruntime 1.16.3（CPU）、OpenCV 4.5.4（带 GStreamer）；无 torch / OpenVINO；PC2 不能上外网。

### 原设计的假设
- 视觉放在 PC2：YOLOv8n 检测人 + CLIP ViT-B/32 匹配衣服描述 → `find` / `approach`（视觉伺服）。
- "≥ 十几 FPS 够用"是**按 CPU 型号估算，未实测**。
- 去门口靠自带 SLAM 导航（不需要额外算力）；大模型和语音识别在云端。

### 风险点
1. **帧率估计偏乐观**：只有 2 个性能核，解码 + 检测 + CLIP + 控制闭环 + Python 单线程限制叠加，实际可能只有估计值的一半。
2. **视频回传方案浪费 CPU**：原计划在 PC2 上叠加检测框再编码成 MJPEG 推流，多了一次 CPU 编码。
3. **视觉无法挪到服务器**：服务器无 GPU，且当前网络下收不到相机组播（在 PC2 内侧 123 网段），必须经 PC2 转发。
4. **CLIP 可能是多余开销**：颜色类描述（红衣服）用人体框上半身 HSV 颜色统计几乎零开销，可能更准；CLIP 只在开放描述（戴帽子、背书包）时才有必要。
5. **重型视觉模型不可行**：GroundingDINO / YOLO-World 等开放词汇检测在这台机器上基本跑不动（目前设计已绕开：去门口用 SLAM）。

### 评估方法（阶段 2 第一步）
在服务器下载 YOLOv8n、CLIP ViT-B/32 的 ONNX，拷到 PC2 做纯计算测速（不碰狗），在 SLAM 常驻的情况下测：
- 相机解码 720p 的 CPU 占用；
- YOLOv8n 单帧耗时（320 / 640 输入）；
- CLIP 每个裁剪图耗时；
- 三者串起来的端到端 FPS。

### 可选方案（按评估结果选档）

| 档位 | 做法 | 代价 / 前提 | 适用 |
|---|---|---|---|
| A（默认） | PC2 CPU：YOLOv8n + 颜色统计，CLIP 可选 | 现成 onnxruntime | 实测 ≥ 8 FPS |
| B | OpenVINO 跑核显 | 服务器下载离线包拷到 PC2 | A 不够 |
| C | **云端视觉模型认人 + 本地轻量跟踪**：通义多模态模型每 1–2s 看一帧给出目标框，本地跟踪器高频跟随 | 识别慢 1–2s、依赖网络；与现有 key 共用 | 本地算力不够 / 描述复杂 |
| D | 加硬件（Hailo 加速模块、Jetson 等） | 采购、确认接口（M.2/USB） | 更复杂的视觉需求 |
